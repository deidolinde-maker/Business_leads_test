# Production: подключение бизнес-форм, 16.09.2026

## Основание и данные

Пользователь подтвердил production и допустимость ранее предоставленного девятизначного телефона, а после двух пилотов явно попросил новую проверку с `9999999999`. Текущий профиль `config/data/samara.json`: `prod`, 10 цифр; замена выполнена по новому указанию пользователя. На Билайне штатная маска добавляет префикс +7; это поведение сайта, не преобразование данных тестом.

Проверка: Chromium 151 / Playwright 1.62.0, отдельные контексты, service workers заблокированы. Во время осмотра и снятия контрактов все изменяющие запросы отменялись. Три переданных production-запроса описаны отдельно ниже.

## Билайн: два заданных поддоменных URL

- `https://samara.beeline-ru.online/business/internet-dlya-biznesa`
- `https://samara.beeline-ru.online/business/mobilnaya-svyaz-dlya-biznesa`

Оба URL вернули 200. `.business_no_address_button` открывает `#popup-business form.wpcf7-form` с CF7 ID 952, unit tag `wpcf7-f952-o3`. Внутри формы отображается Самара / `data-item=36401`.

В каждой форме штатно заполнены адрес и телефон; целевой POST перехвачен и отменён до передачи. Подтверждён multipart:

| Поле | Значение |

| BusinessCityId | `36401` |
| CityName | `Самара` |
| FormName | `Заявка Бизнес` |
| lead_form_type | `forma_podklyucheniya_biznes` |

| _wpcf7 | `952` |

Endpoint: `https://samara.beeline-ru.online/wp-admin/admin-ajax.php?action=cf7_proxy_submit_transport&cf7_form_id=952&cf7_operation=feedback`.

Тот же путь обслуживает GET схемы форм 949/950/951/952 с `cf7_operation=schema`. Точные наблюдённые URL добавлены как read-only исключения. Другой query/method не обходит контроль отправки. POST-исключения на общем пути submit запрещены.

Положительное ожидание взято из развёрнутого JS: CF7 использует `status=mail_sent`, обработчик `wpcf7submit` переводит на `/thanks` только при этом статусе. Это основание ожидания, не утверждение о полученном положительном ответе.

Просмотрены скрипты страницы и ресурсы `/wp-content/themes/beeline/js/main.js`, `cf7-address-search.js`, `/wp-content/plugins/contact-form-7/includes/js/index.js`. Снимки и перехваченные запросы с замаскированным телефоном сохранены локально в ignored `artifacts/onboarding-20260916/`; динамические подписи и идентификаторы аналитики в Git не копируются.

## Первый реальный пилот: интернет для бизнеса

- Результат: **FAIL**, 18.62 с всего pytest; фазы кейса: 1.406 с navigation, 0.062 с form, 0.032 с region, 0.125 с fill, 15.078 с submission.
- Проверки региона, бизнес-признака и идентичности пройдены до передачи.
- `observed=1`, `forwarded=1`; получен HTTP 200.
- Переход `/thanks` не подтверждён. `mail_sent` и доставка заявки в CRM **не подтверждены**.
- Ошибка отчёта: `unexpected_write_endpoint`. Во время предыдущих перехватов наблюдались фоновые POST Яндекс.Метрики; первая версия диагностики не сохраняла путь заблокированного запроса и все последующие причины, поэтому окончательная причина ответа формы неизвестна.
- Первая заявка повторно не отправлялась. Артефакт: `artifacts/prod-pilot-beeline-internet/beeline-business_page-samara-internet-dlya-biznesa/result.json` и маскированный screenshot.

После пилота добавлены список ошибок, `response_accepted`, стандартный машинный `response_status` и путь неожиданного запроса без query/body. Три наблюдённых пути аналитики настроены на отмену без ошибки бизнес-кейса; их запросы по-прежнему не передаются. Ненастроенный POST остаётся ошибкой.

Первоначально автоматическая проверка разрешений остановила второй кейс. После отдельного ответа пользователя «Да, отправить одну заявку» он выполнен ровно один раз, см. результат ниже. Конфигурация двух кейсов `active` означает готовность механизма к запуску, а не успешную отправку или разрешение на повтор первого пилота.

## Второй реальный пилот: мобильная связь для бизнеса

- Пользователь отдельно разрешил одну заявку на этой странице с тем же профилем.
- Результат: **FAIL**, 19.04 с всего pytest; фазы: 2.281 с navigation, 0.047 с form, 0.031 с region, 0.094 с fill, 15.062 с submission.
- Перед отправкой проверены Самара/36401, бизнес-признак и идентичность формы.
- `observed=1`, `forwarded=1`, HTTP 200, **`response_status=validation_failed`**, `response_accepted=false`.
- Сервер отверг данные. Это не успешная бизнес-заявка и не подтверждение доставки в CRM. Повторного submit не было; три фоновых запроса отменены без ошибки кейса.
- GET-схема формы 952 содержит required City, required Phone и tel Phone. Она не указывает, какое поле вызвало конкретный серверный отказ; дополнительные серверные проверки также неизвестны. Нельзя объявлять номер причиной отказа только по длине.
- Поля ошибки первого ответа не сохранялись. После этого прогона добавлено сохранение только безопасных `invalid_fields[].field` (без сообщений и значений) и локальная проверка этой диагностики. Новая production-заявка ради диагностики не отправлялась.
- Артефакт: `artifacts/prod-pilot-beeline-mobile/beeline-business_page-samara-mobilnaya-svyaz-dlya-biznesa/result.json`.

Первые два пилота передали **2 production-запроса, по одному на каждую страницу Билайна**. Оба кейса FAIL. МТС и Ростелеком заявок не отправляли.

## Третий прогон: 10 цифр по прямому указанию пользователя

На той же странице мобильной связи выполнен один новый запуск с `9999999999`, адрес не менялся.

- Передан **ровно один POST**, регион Самара/36401 и бизнес-признак проверены.
- HTTP 200, **`response_status=mail_sent`**, `invalid_field_names=[]`, `response_accepted=true`.
- Ожидание перехода на `https://samara.beeline-ru.online/thanks` прошло; ошибка возникла после него в проверке счётчика запросов.
- Бизнес-форма подтвердила успех. После прогона пользователь сообщил: «В црм заявка пришла, все ок». Доставка в CRM подтверждена пользователем 16.09.2026; агент не выполнял отдельную CRM/MCP-проверку, ID записи не предоставлен.
- Технический итог pytest: FAIL `duplicate_submission`, 5.86 с; `observed=2`, но `forwarded=1`.
- В развёрнутом CF7 JS после `mail_sent` вызывается reset формы и GET `contact-forms/952/refill`; транспорт перенаправляет этот GET на общий admin-ajax endpoint. Это объясняет вероятную причину второго срабатывания перехвата. В прогоне метод/query второго запроса не сохранялись, поэтому его полная идентичность не восстановлена по логу.
- По проверенному клиентскому коду добавлено точное GET-исключение `cf7_form_id=952&cf7_operation=refill`. Проверка метода/URL теперь предшествует счётчику повторных отправок: неизвестный соседний запрос не называется дубликатом POST. Реальный второй feedback POST по-прежнему запрещён.
- 16 локальных браузерных проверок прошли за 18.61 с; одна воспроизводит POST → GET refill и подтверждает один переданный/учтённый submit. Отдельный тест повторного POST продолжает проверять блокировку.
- Повторной production-отправки после этого исправления не было; исторический FAIL не переписан в PASS.
- Артефакт: `artifacts/prod-pilot-beeline-mobile-10digits/beeline-business_page-samara-mobilnaya-svyaz-dlya-biznesa/result.json`.

Итого за весь этап передано **3 POST: 1 на интернет для бизнеса, 2 на мобильную связь** (сначала 9 цифр, затем отдельно запрошенные пользователем 10). Для последнего прогона подтверждены `mail_sent`, `/thanks` и доставка в CRM со слов пользователя. Это подтверждение конкретного сценария мобильной связи Билайна; оно не распространяется на остальные страницы и не меняет исторический технический FAIL pytest. Первые два прогона успешной доставки не подтвердили.

## МТС: первоначально заданные страницы и последующее уточнение

В DOM обнаружена форма проверки адреса CF7 638 с radio `Place=Для бизнеса`; это другой путь. На момент осмотра её индикатор содержал Самару без `data-item`; поля `CityName` и `City` были пустыми. Внешний маршрут не открывался, заявки МТС не отправлялись.

Позже пользователь уточнил: отдельные бизнес-формы MTS работают только на `https://mts-home-online.ru/`, речь именно о business pages, не checkbox. Обе первоначальные страницы переведены в `excluded`; актуальная цель и её read-only проверка описаны в [MTS business scope](mts-business-scope-20260916.md).

## Ростелеком: R1 без поддомена

На `https://rtk-internet.online/business` карточка «Интернет для бизнеса» открывает `#popup-business form` (CF7 3826). На странице пять одинаковых классов кнопок, поэтому локатор ограничен точным названием карточки.

Кнопка выбора города: `.autocomplete-city.button-select-city`. Попап: `#popup-select-city`; поиск: `input#city-input`; найденная ссылка: `a.region_item.region_link[id='36401']`, текст Самара, href `https://rtk-internet.online/samara`.

При клике из бизнес-попапа навигации нет: конечный URL остаётся `/business`, попап выбора закрывается, индикатор становится Самара / 36401, скрытые `CityName=Самара`, `BusinessCityId=36401`; поле адреса разблокируется. Конфиг R1 обновлён для этого фактического поведения и проверен штатными `FormAdapter.open_form` / `ensure_samara` без submit.

При этом скрытое описательное поле `Info` после выбора всё ещё содержало «Город: Москва». Submit не нажимался; неизвестно, обновляет ли его обработчик отправки. До проверки согласованности исходящего запроса и ответа кейс остаётся blocked. Телефон/адрес здесь не заполнялись, внешних заявок нет.
