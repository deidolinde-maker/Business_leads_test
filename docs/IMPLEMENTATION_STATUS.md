Актуальное продолжение от 16.09.2026: [production-подключение](evidence/production-onboarding-20260916.md). Окружение и телефон подтверждены, 2 active / 264 blocked, 46 локальных проверок пройдены. Оба production-пилота завершились FAIL, по одному переданному запросу; второй вернул `validation_failed`, доставка не подтверждена. Ниже сохранён исторический отчёт стартового этапа.

Обновление 16.09.2026: добавлены [четыре самарских поддоменных маршрута от пользователя](SAMARA_ROUTES.md). Текущий реестр содержит 266 blocked-записей; приведённые ниже 262 записи и результаты прогона относятся к первоначальному снимку 15.09.2026.

## Реализовано и проверено локально

- Независимый пакет Python 3.12 / pytest / Playwright, без runtime-импортов двух старых sender-ов.
- Единственный целевой город Самара, UI ID 36401; иной город в case/data/contract не допускается.
- R1: выбор через поле поиска и точную ссылку, переход /samara и восстановление подтверждённой бизнес-страницы. R2: прямой вход с проверкой конечного URL и региона формы.
- Поддержка штатного checkbox (включая скрытый input с label) и radio; обратное переключение без небизнес-отправки.
- Контроль региона после переключений и заполнения, отдельные consent selectors.
- Проверка region/business/identity фактического POST до передачи; неверный регион отменяется без исправления payload.
- Одна отправка; JSON, form-urlencoded, текстовый multipart; связанный ответ и UI-подтверждение; отсутствие retry-submit.
- Раздельные результаты, 75-секундный deadline и фазовые тайминги, скриншот ошибки с маскировкой полей.
- collect-only и summary без ложного live-PASS; blocked-кейсы не запускают браузер.
- GitHub Actions для local checks; отдельный Jenkinsfile local/collect/live. Jenkins job пока не создавался.

## Результаты проверки

37 локальных тестов прошли за **21.39 с** в Chromium 151 / Playwright 1.62.0 на Windows. В том числе:

- успешные R1/R2: сервер локального fixture получил ровно одну бизнес-заявку Самары;
- UI Самара, outgoing другой регион: сервер получил **0** заявок;
- обычный тип заявки вместо business, сброс города и ложный Thanks: FAIL;
- повторный запрос заблокирован; сервер получил только первый запрос;
- отказ обработчика не приводит к повторной отправке;
- частичный успех не скрывает отдельную ошибку;
- отсутствующие контракты, окружение и пустой scope не дают green.

Сборка полного исходного набора через collect-only: **262 записи за 0.27 с**, все обозначены blocked; это не E2E-результат. Успешные unit/fixture-проверки подтверждают реализацию механизмов, не состояние провайдерских сайтов и не live-SLA.

`business_cases.json`: 16 URL бизнес-страниц и 246 страниц-кандидатов на бизнес-переключатель. Это инвентаризация для подключения, не доказательство наличия 262 форм. Несколько независимых форм на одном URL при осмотре должны стать отдельными active-кейсами; отсутствие бизнес-control должно получить подтверждённое исключение. Исходные города не являются live-целями.

`locator_sources.json`: импортированные FORM_CONFIGS, POPUP_BUTTON_CLASSES, SERVICE_PLACE_VALUES. Они сохраняют точные значения источников, но широкие fallback не становятся рабочими селекторами нового active-кейса без проверки.

## Что требуется перед первым реальным прогоном

1. Указать **stage или production**. Пользователь сообщил адрес/телефон, но пока не выбрал окружение.
2. Проверить хотя бы один реальный самарский маршрут и локаторы целевой формы/кнопки региона.
3. Получить реальное представление Самары и бизнес-признака в outgoing запросе, идентичность формы и положительный ответ. Имена этих полей старые тесты не проверяли, поэтому они не выдуманы.
4. Проверить профиль данных: **Самара, Ленинградская, 1**, телефон **999999999** сохранён буквально. Это 9 цифр; совместимость с фактической маской не подтверждена, дополнение цифрами не выполнялось. Если форма требует другие реквизиты, их также нужно определить.
5. Записать evidence, подтвердить environment профиля и перевести соответствующий кейс в active.

Эти пункты не мешали стартовой разработке. Они блокируют live-отправку, а не локальную проверку механизма.

## Границы первого этапа

- Ни одной заявки на внешние сайты не отправлено.
- Исходные Everyday_test и Big_landing_test не менялись: их миграция откладывается до подтверждения нового live-набора, чтобы не потерять действующее покрытие.
- Активных производственных сценариев пока **0**. Не подтверждены все реальные формы, Самара на каждом домене, CRM-доставка и скорость внешних сайтов.
- GET-submit/WebSocket/file upload и специальные региональные контракты требуют отдельного адаптера; не включаются автоматически.
- Параллельность пока W=1; мобильные профили и общая регрессия сайта не входят в стартовый этап.
