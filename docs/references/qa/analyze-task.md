# Анализ любой QA-задачи

## Цель

Превратить свободное описание задачи в проверяемый QA-план, адаптированный к продукту, домену, риску и доступным ресурсам.

## Входные данные

- описание цели и ожидаемого поведения;
- требования, макеты, API-контракт или ссылки на код;
- тип продукта: web, mobile, API, desktop или смешанный;
- роли пользователей и затронутые интеграции;
- окружения, ограничения и доступные инструменты.

## Алгоритм

1. Переформулировать цель задачи и выделить критерии приемки.
2. Определить затронутые компоненты, пользовательские пути и внешние зависимости.
3. Найти неоднозначности и сформировать только критичные вопросы.
4. Оценить риски по влиянию, вероятности и сложности обнаружения.
5. Выбрать техники тест-дизайна для каждого риска.
6. Определить уровни тестирования: unit, API, integration, UI, end-to-end.
7. Составить позитивные, негативные, граничные и exploratory-проверки.
8. Отдельно определить, что автоматизировать сейчас, позже или не автоматизировать.
9. Зафиксировать допущения, тестовые данные и критерии завершения.

## Формат результата

Использовать шаблон из `../templates/qa-analysis.md`. Каждый существенный вывод должен ссылаться на требование, артефакт проекта или явно отмечаться как рекомендация.

## Ограничения

- Не считать отсутствие ошибки доказательством корректности.
- Не генерировать тесты для неизвестных бизнес-правил без маркировки допущений.
- Не рекомендовать UI-автоматизацию там, где стабильнее проверить API или доменную логику.
- Не скрывать пробелы в требованиях.
