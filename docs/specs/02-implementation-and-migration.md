# Реализация и миграция отдельного теста бизнес-заявок

Статус: проект технической спецификации, ревизия 2 — отправка только в Самаре. Репозиторий: [deidolinde-maker/Business_leads_test](https://github.com/deidolinde-maker/Business_leads_test), ветка по умолчанию main. Репозиторий уже создан и на момент проверки пустой.
[Функциональные требования и критерии приёмки](01-business-test-spec.md).

## 1. Архитектура

Один параметризованный тест `test_business_submission(case)`; один case — один независимый пользовательский путь до бизнес-отправки **в Самаре**. Регион фиксирован требованиями и не является расширяемой матрицей городов.

Предлагаемая структура нового репозитория:

```text
Business_leads_test/
  pyproject.toml
  README.md
  conftest.py
  config/
    business_cases.json
    contracts/
  business/
    cases.py
    adapters.py
    controls.py
    region.py
    submission.py
    result.py
  tests/
    test_business_submission.py
    unit/
  Jenkinsfile
```

Это проектируемые пути; репозиторий существует, перечисленные файлы пока не созданы. Формат JSON выбран как простой проверяемый реестр; пути к секретам/данным передаются через конфигурацию окружения.

### Ответственность компонентов

| Компонент | Ответственность |
|---|---|
| cases.py | Загрузка, валидация и фильтрация реестра; уникальность ID; пустая выборка; учёт blocked/excluded |
| adapters.py | Известные различия форм: открытие, поля, адресные подсказки, submit; ограниченные подтверждённые fallback |
| controls.py | Явное управление бизнес-control и отдельное управление согласиями |
| region.py | Фиксированная Самара, маршруты R1/R2, выбор через попап, повторная проверка региона в целевой форме |
| submission.py | Проверка Самары до передачи запроса, сопоставление запроса и ответа, проверка бизнес-признака, отсутствие повторного submit |
| result.py | Результат кейса, тайминги, диагностика и итоговое покрытие |
| conftest.py | Параметризация, browser/context, параметры запуска; не импортирует исходные монолиты |
| test_business_submission.py | Короткая последовательность из функциональной спецификации, без обхода сайта |
| Jenkinsfile | Отдельный pipeline этого репозитория; запуск и отчёт не зависят от двух старых job-ов |

Процесс браузера переиспользуется в пределах worker-а. Context, cookies, локальное хранилище, сетевые наблюдения и page изолированы по кейсу. Контекст закрывается в finally, в том числе при таймауте.

## 3. Контракт адаптера

Для каждого адаптера требуются операции:

1. `open_entry(page, case, deadline)` — бизнес-URL без региона для R1 либо прямая самарская бизнес-страница для R2.
2. `open_form(page, case, deadline)` — вернуть единственный целевой form locator.
3. `ensure_samara(page, form, case, deadline)` — R1 выбирает Самару через попап, R2 проверяет уже открытый город; вернуть актуальный locator формы после возможной навигации.
4. `set_business_state(form, case, deadline)` — пользовательское действие, проверка фактического состояния.
5. `fill_required_fields(form, data, contract, deadline)` — самарские данные без изменения бизнес-режима и региона.
6. `assert_ready(form, case)` — бизнес-режим, Самара/36401, необходимые поля и согласия.
7. `submit_once_and_observe(page, form, contract, deadline)` — проверить Самару до передачи целевого запроса, один клик, фактический request/response.
8. `assert_business_submission(observation, contract)` — бизнес-признак, регион Самара и положительный ответ.
9. `assert_confirmation(page, observation, contract, deadline)` — подтверждение текущей отправки.

Точные имена методов — предлагаемое API. Внутреннюю реализацию можно уточнить при сохранении ответственности.

### Элементы управления

- Для обычного checkbox использовать штатное действие и проверку checked.
- Для скрытого input с пользовательским label кликать связанный видимый control, затем проверять underlying state.
- Прямое присваивание `checked=true` через JS не подтверждает доступность пользовательского выбора.
- Согласия имеют отдельные точные селекторы; сканирования «отметить все checkbox» нет.
- Если business-control меняет структуру формы, заново получить локаторы нужных полей.
- У radio проверяется выбранный бизнес-вариант и отсутствие выбора альтернативы в той же группе.
- Для поддерживаемого обратного переключения не отправлять небизнес-заявку; после переходов окончательное состояние — business.
- Fallback должен сохранять идентичность формы и проверять результат действия, а не только отсутствие исключения.

### Регион Самара: реализация R1/R2

Фиксированные требования: `TARGET_CITY_NAME = "Самара"`, `TARGET_CITY_UI_ID = "36401"`. UI ID взят из сообщения пользователя; имя backend-поля и его система ID определяются контрактом сайта, автоматически не приравниваются к UI ID.

Для предоставленной разметки:

- текущий город: `span#autocomplete_city_name.autocomplete-city-name` в целевой форме; проверять точный текст и data-item;
- поиск: `input#city-input.popup-select-city__input` в активном попапе;
- результат: `a.region_item.region_link[id="36401"]` с точным текстом `Самара` и ожидаемым href; использовать attribute selector для числового ID;
- кнопку открытия искать по подтверждённому DOM-контракту адаптера: span может быть только содержимым кнопки.

R1: открыть нужную форму → нажать селект региона → ввести Самара → выбрать точное совпадение → дождаться обновления/перехода → восстановить нужный бизнес-контекст по проверенному маршруту → повторно найти форму и проверить Самару. Ссылка `https://rtk-internet.online/samara` сама по себе не подтверждает business URL. Не переносить её hostname на другие лендинги.

R2: сразу открыть подтверждённый бизнес-URL Самары на региональном поддомене → проверить конечный URL и город формы. Если host соответствует Самаре, но форма показывает другой регион, завершить FAIL до submit. Не переключаться на другой маршрут молча, скрывая дефект прямого входа.

Для каждого переключения бизнес-control, перерисовки формы и непосредственно перед submit вновь проверять город. Поиск в header или другой скрытой форме не подменяет проверку выбранной формы заявки.

Контекст кейса изолирован: выбор Самары не считается выполненным на основании cookies предыдущего кейса. При R1 нельзя ускорять проверку установкой cookie/локального storage или JS-присваиванием data-item вместо штатного выбора.

## 4. Сетевая проверка

Перед кликом установить перехват и наблюдение за запросом по host/path, HTTP method, форме и иным признакам её фактического контракта. Ответ брать от **этого же Request**, а не от любого ответа с похожим URL.

**Требование «только Самара» выполняется до фактической передачи:** разобрать регион целевого запроса по проверенному region_submission_contract; если регион другой, отсутствует обязательное поле или сопоставление не определено — отменить запрос и завершить кейс ошибкой. Корректный запрос передаётся без изменения данных. Проверка ответа после отправки не заменяет этот барьер.

Перехват должен охватывать реальные механизмы отправки конкретной формы: document POST, fetch/XHR и применимые redirect-hop по контракту. Для Playwright route учитывать service workers: в базовом профиле блокировать их, если иначе запрос обходит перехват; совместимость такого профиля с лендингом проверить. Неперехватываемый механизм — blocked до реализации контроля, а не разрешение отправлять без проверки. Остальной трафик не модифицируется.

Если регион хранится в нескольких полях/URL, проверить их согласованность. Пара «UI Самара / запрос Москва» должна дать ноль переданных заявок. Подменять регион в payload на Самару, чтобы тест прошёл, нельзя. Для региона, определяемого только серверной сессией, до active нужен проверяемый способ гарантировать Самару до submit; одной надписи в UI недостаточно.

Поддерживаемые форматы тела — только реально используемые адаптерами: JSON, form-urlencoded, multipart. После разбора проверить бизнес-поля, регион и их типы. Код не должен заранее объявлять, что business всегда передаётся как `Place="Для бизнеса"` или `is_business=true`, а регион — как `region_id=36401`.

Для корреляции использовать существующие поля формы/ответа; не добавлять произвольные параметры в production-заявку.

Ошибки различать:

- форма не найдена;
- бизнес-control отсутствует/не переключился;
- попап региона не открылся / Самара не найдена / выбор города не применился;
- регион не Самара или противоречат текст и data-item;
- регион сбросился при смене услуги/перерисовке;
- запрос заблокирован до передачи: регион другой или не подтверждён;
- данные/валидация не позволяют submit;
- целевой запрос не отправлен;
- бизнес-признак не совпал;
- сервер отклонил заявку;
- ответ не получен после отправки;
- UI-подтверждение отсутствует;
- превышен deadline.

Дублирующий целевой запрос, наблюдаемый в границах выполнения одного кейса, фиксируется как ошибка с приложенными идентификаторами. Это не доказывает отсутствие возможных отложенных дублей за пределами наблюдения.

Если форма требует серверной сверки созданной заявки: использовать полученный реальный ID и узкий read-only endpoint выбранного окружения. Доступный stage-инструмент `mcp__stage_qa_mcp__orders_get_status(uuid)` — кандидат для исследования контракта, но его схема сама по себе не гарантирует наличие бизнес-типа в ответе. Не подменять отсутствие контрактных полей предположениями и не выполнять массовый поиск заявок.

## 5. Предлагаемый интерфейс запуска

Команды ниже — требования к будущему CLI, сейчас не реализованы:

```text
pytest tests/test_business_submission.py --env=stage --provider=rostelecom
pytest tests/test_business_submission.py --env=stage --case-id=<ID_из_реестра>
pytest tests/test_business_submission.py --env=stage --collect-only
pytest tests/test_business_submission.py --env=prod --provider=beeline
```

- `--env` обязателен, stage/prod URL берутся из конкретных записей.
- Город фиксирован: Самара. Не вводить CLI/CI-параметр, позволяющий отправить в другой город; конфигурация с иной target_city отклоняется до запуска браузера.
- Отсутствие provider/case-id выбирает все записи данного окружения.
- Совместимые фильтры применяются пересечением; пустой результат — ошибка конфигурации.
- Выбор provider не должен запускать обычные заявки этого провайдера.
- collect-only выдаёт выбранные ID, Самару, режим R1/R2, входные/целевые URL, количество active/blocked/excluded и причины; не открывает сайты и не отправляет заявки.
- Базовый профиль — Chromium desktop, W=1; увеличение W только после проверки допустимой нагрузки и независимости данных.
- Отдельные конфигурации подготовки/UI-проверок, если понадобятся, имеют другой тип результата и не выдают PASS отправки.
- Никаких режимов core/variants, меняющих смысл бизнес-покрытия: фильтры меняют только явно выбранную область.

## 6. Отчёт и CI

Один кейс — один pytest item / Allure result. В карточке кейса:

- case_id, окружение, provider, исходный и конечный URL;
- вид бизнес-сценария и идентичность формы;
- наблюдённое бизнес-состояние;
- целевой город Самара, наблюдённые текст/data-item, режим R1/R2, href выбранного города и конечный бизнес-URL;
- фактическое сетевое представление региона и результат проверки до передачи: allowed / blocked;
- endpoint, HTTP status и результат проверки бизнес-признака;
- ID заявки, если возвращается, без выдуманных UUID;
- длительность каждой фазы и всего кейса;
- причина ошибки, скриншот и при необходимости trace с обработкой чувствительных данных.

Итоговый machine-readable summary включает selected, passed, failed, blocked, excluded, incomplete и wall time. PASS допускается только при passed=active для выбранной области и отсутствии blocked/incomplete/failed. Явно excluded остаются видимыми как исключения покрытия.

Отдельный job запускается вручную по окружению/провайдеру/ID, публикует результаты даже при ошибке теста и возвращает ненулевой код при ошибках запуска или неполном обязательном покрытии. Сбой публикации отчёта отражается отдельно и не превращает падение тестов в green.

Существующие уведомления двух репозиториев не копировать автоматически. Назначение канала и расписание — отдельные настройки после реализации.

## 7. План миграции

### Этап A. Инвентаризация

1. Зафиксировать актуальные SHA обоих источников.
2. Взять список бизнес-страниц из скоупов двух исходных тестов и собрать объединение:
   - business-форм и основных/региональных бизнес-страниц;
   - форм с Place business;
   - checkbox «Для бизнеса / в офис»;
   - connection/checkaddress и иных технических форм на бизнес-путях;
   - закомментированных и временно выключенных бизнес-сценариев.
3. Для каждого исходного пути установить R1/R2 и самарскую цель; московские и прочие города сохранить только как provenance. Не получать самарский URL глобальной заменой строки moskva или DEFAULT_CITY.
4. Сверить DOM/исходники: новая индикация города, кнопка региона, поиск, ссылка Самары, business-control и контракт отправки. Точные неизвестные маршруты оставить blocked.
5. Создать таблицу переноса с колонками: source_repo, source_sha, source_case, source_page_url, target_case_id, region_mode, samara_business_url, environment, status, reason, evidence. Объединять дубликаты после сопоставления самарских целей, сохраняя различные формы и способы входа.
6. Подтвердить самарские тестовые адреса и ожидаемые бизнес/региональные признаки запроса.

Ни удаление /business строк из allowlist, ни исключение form_type=business сами по себе не означают полного отделения.

### Этап B. Реализация нового репозитория

1. Независимые зависимости, конфиг, валидация и параметризация.
2. Минимальные адаптеры для подтверждённых групп форм.
3. Выбор/проверка Самары R1/R2, бизнес-control, сетевой контракт с блокировкой другого региона до передачи и один submit.
4. Deadline, изоляция context, диагностика.
5. Отдельный pipeline и summary.
6. Локальные контрактные проверки логики и затем точечная проверка доступных stage-кейсов.

Недоступный stage-аналог не подменяется production URL. Для него результат подготовки — blocked до определения подходящего проверочного контура.

### Этап C. Отделение в двух основных репозиториях

**Everyday_test:**

- Удалить бизнес-шаги 3/4b из основного маршрута, а не оставлять их условным зелёным пропуском.
- Исключить целевой бизнес-вариант из основных запусков all/variants.
- Исключить бизнес-пути с другими техническими именами форм.
- Заменить массовую отметку чекбоксов на явные согласия; в обычных кейсах задать и проверить небизнес-состояние.
- Убрать неиспользуемые business-конфиги/селекторы только после проверки всех ссылок.
- Сохранить небизнес-пути главной и города.

**Big_landing_test:**

- Вывести business suite из основного маршрута и CI-матрицы.
- Удалить временный ENABLE_BUSINESS_SUBMIT_STEPS из действующего пути после переноса его ответственности.
- Разделить URL/кейсы, где business заявка создаётся через connection; не удалять все connection-проверки.
- Исключить бизнес-варианты Place и бизнес-чекбоксы из основных отправок.
- Очистить бизнес-ожидания, aliases и allowlists только там, где они больше не нужны обычным кейсам.
- Убрать business-only элементы, которые сейчас проходят без действий; документация указывает новый репозиторий.

**Общее правило:** классифицировать перенос по семантике заявки, URL и контракту, а не только по строке business. Если обычная форма исходно находится в business-состоянии, основной тест должен выбрать подтверждённый небизнес-вариант; если такого пути нет — кейс принадлежит новому репозиторию.

Защита основных прогонов проверяется на локальном перехвате/стабе запросов: ни один путь заполнения, retry или восстановления не должен отправить business payload. Простое удаление строки из SERVICE_PLACE_VALUES недостаточно.

### Этап D. Переключение и приёмка

1. Проверить соответствие исходного и нового реестров до отключения ответственности в старых job-ах.
2. Подготовить три согласованные группы изменений: новый репозиторий, Everyday_test, Big_landing_test.
3. Выполнить точечные прогоны нового набора на согласованном окружении и проверки сохранности небизнес-сценариев.
4. Переключить расписания/владение сценариями так, чтобы один бизнес-кейс имел одного активного отправителя.
5. Не запускать старый и новый live-sender одновременно ради сравнения; сравнить код/collect-only, затем последовательные согласованные проверки.
6. Зафиксировать полный результат переноса, исключения и замеры скорости.

При откате сначала отключается соответствующий новый запуск, затем восстанавливается предыдущая конфигурация. Временная потеря покрытия явно отражается; старые отключённые business-шаги не считаются работоспособным запасным тестом.

## 8. Проверки реализации

| Проверка | Уровень и ожидаемый результат |
|---|---|
| Пустой фильтр, дубли ID, неполный active контракт | Локальная проверка реестра: ошибка до браузера |
| Ожидаемый control исчез | UI fixture: FAIL вместо пропуска |
| Клик выполнен, checked не изменился | UI fixture: FAIL |
| Общие согласия затрагивают business-control | UI fixture: выявить изменение и FAIL |
| R1: Самара выбирается по точному ID и тексту | UI fixture/live: попап открыт, выбор применён, целевая форма показывает Самару/36401 |
| В результатах есть Самарская область или чужой ID | UI fixture: не выбрать похожий результат; без точной Самары FAIL, ноль переданных заявок |
| Выбор ссылки ведёт на /samara без business | UI fixture: вернуть подтверждённую бизнес-форму и повторно проверить регион перед submit |
| R2: прямой URL поддомена Самары | Открытие сразу нужного URL; проверка host/path и Самары в форме без обхода других городов |
| UI текст Самара, data-item другой; или наоборот | UI fixture: FAIL до клика submit |
| Смена бизнес-control сбрасывает регион | UI fixture: повторная проверка обнаруживает сброс; ноль переданных заявок |
| UI Самара, outgoing запрос другого региона | Перехват до сети: запрос отменён, FAIL, счётчик серверных приёмов равен нулю |
| Региональный контракт неизвестен | Ошибка конфигурации до live-submit |
| Несколько форм/скрытых полей города на странице | UI fixture: проверяется регион именно отправляемой формы |
| В конфиг/CLI передан другой город | Ошибка до браузера; не допускается наследование Москвы из старых конфигов |
| В payload отсутствует/неверен бизнес-признак | Перехваченный запрос: FAIL даже при Thanks |
| Получен ответ от другой формы | Stub: не принимает его за подтверждение |
| Старый success URL/старая вкладка | Stub/UI fixture: не подтверждает текущий submit |
| Сервер принял запрос, ответ потерян | Stub: один клик, неподтверждённый результат, без retry-submit |
| Один кейс успешен, соседний business упал | Запуск двух items: общий незелёный итог |
| Сработал deadline | Незавершённый кейс виден, следующий кейс независим |
| Основные тесты после переноса | Перехват исходящих запросов: business payload отсутствует, обычный остаётся |
| Подтверждённый бизнес-кейс | Целевой live-прогон на выбранном окружении с согласованными данными |
| Скорость | N/W, phase timings, p95 и общий runtime; сравнение при эквивалентном покрытии |

Синтетические страницы и stubs применяются для проверки логики теста; они не заменяют доказательство работоспособности реальных бизнес-форм.

## 9. Готовность к передаче

Результаты реализации: отдельный репозиторий, явный реестр, контрактные адаптеры, независимый тест и CI, таблица переноса, изменения двух источников, отчёт о проверках и скорости.

Для подписания результата использовать AC-01…AC-18 из функциональной спецификации. Все live-кейсы ограничены Самарой. Неизвестные контракты/данные и blocked-сценарии оставлять видимыми, а не заполнять предположениями.
