# Спецификация: отдельный тест бизнес-заявок

Статус: проект спецификации для реализации. Дата: 15.09.2026.

## 1. Цель и согласованный контекст

Создать **отдельный репозиторий** с быстрым независимым тестом бизнес-заявок. Перенести в него бизнес-сценарии из Everyday_test и Big_landing_test, включая выбор «Для бизнеса / в офис» внутри обычных форм.

Подтверждено пользователем: отдельный репозиторий; узкая задача; быстрый прогон; отделение от основных тестов; **все заявки отправляются только в городе Самара**. Репозиторий: [deidolinde-maker/Business_leads_test](https://github.com/deidolinde-maker/Business_leads_test), clone URL: `https://github.com/deidolinde-maker/Business_leads_test.git`.

Ревизия 2: добавлен обязательный выбор/контроль Самары. По GitHub MCP репозиторий существует, default branch — main; на момент проверки он пустой. Данная работа обновляет спецификации, а не реализует или публикует тест.

Предлагаемая реализация — Python + pytest + Playwright, один параметризованный тест на один бизнес-сценарий. Численные бюджеты, интерфейсы запуска и структура ниже являются проектными решениями, а не уже существующими правилами продукта.

**Результат:** независимый запуск даёт однозначный ответ по каждому включённому бизнес-сценарию: форма открылась, выбрана Самара, бизнес-состояние установлено, отправлена бизнес-заявка именно для Самары, получен связанный с ней положительный ответ.

## 3. Границы нового теста

| Входит | Как проверяется |
|---|---|
| Выделенная форма на бизнес-странице | Вход по нужному URL, выбор/проверка Самары, одна конкретная форма, одна бизнес-отправка |
| «Для бизнеса» в группе Place | Целевой бизнес-вариант, проверка выбранного состояния и запроса |
| Чекбокс «Для бизнеса / в офис» | Явный выбор, проверка состояния, одна бизнес-отправка |
| Форма connection/checkaddress или другой технический тип, создающий бизнес-заявку | Включается по назначению и контракту, независимо от имени CSS-класса |
| Региональный бизнес-URL | Только бизнес-страница Самары; другие города сохраняются как источники переноса, не как цели отправки |
| Закрытие мешающих оверлеев, заполнение адреса, телефона и согласий | Только подготовка целевой бизнес-формы |

В основной прогон нового репозитория не входят: отправки в квартиру/частный дом, самостоятельная проверка profit-попапов, обход каталога и всех CTA, выбор всех городов, проверка возврата с Thanks, мобильные тарифы, SEO, общий аудит сайта.

Автоматически появившийся посторонний попап закрывается. Если он мешает целевой форме и не закрывается, бизнес-кейс получает ошибку подготовки; отправлять из него другую заявку для продолжения нельзя.

## 4. Реестр сценариев

Источник списка бизнес-страниц — объединение скоупов Everyday_test и Big_landing_test, как указал пользователь. На его основе формируется версионируемый явный реестр нового теста с целевым городом Самара. Обнаружение форм на странице используется для проверки записи реестра, а не для молчаливого сокращения покрытия.

### 4.1. Поля записи

| Поле | Требование |
|---|---|
| case_id | Уникальный стабильный идентификатор |
| provider | Провайдер из подтверждённого контекста |
| environment, page_url | Явное окружение и точный проверенный URL; stage и prod хранятся отдельно |
| target_city, target_city_ui_id | Фиксированные значения `Самара` и `36401` для предоставленного UI-контракта; другой город запрещён |
| region_mode | `popup_selection` для входа без региона или `direct_city_subdomain` для прямого входа на бизнес-страницу Самары |
| source_page_url, samara_business_url | URL из старого скоупа и проверенный бизнес-URL назначения в Самаре; их нельзя автоматически считать одинаковыми |
| region_control | Locator текущего города, кнопки открытия селекта, поля поиска и точной ссылки Самары в активном попапе |
| region_submission_contract | Где регион реально определяется в запросе: поле/поля, URL или иной подтверждённый механизм; соответствие Самаре проверяется до передачи запроса серверу |
| flow_kind | business_page / business_option; для страницы с переключателем также задаётся business_control |
| form_adapter | Адаптер фактической структуры формы; имя connection не исключает бизнес-назначение |
| form_identity, trigger | Устойчивая идентификация формы и нужного триггера либо указание inline |
| business_control | none / checkbox / radio / другой подтверждённый тип; селектор, пользовательский способ выбора, ожидаемое состояние |
| field_contract | Нужные поля, условная видимость/обязательность, подсказки адреса — из текущей формы и требований |
| data_profile | Ссылка на согласованный профиль тестовых данных |
| submission_contract | Идентификация запроса, бизнес-признак или специализированный endpoint, ожидаемый ответ и способ корреляции |
| confirmation | Проверенный способ UI-подтверждения именно этой формы |
| source_refs | Репозиторий, SHA, исходный сценарий/конфиг; при объединении — ссылки на оба источника |
| status, reason | active / blocked / excluded; для двух последних причина и ссылка на решение/дефект |
| verification | Когда и на каком окружении подтверждены URL, селекторы и контракт |

В active нельзя перевести запись без установленных URL, бизнес-признака, контракта региона Самара и тестовых данных. Незаполненный контракт — блокирующая ошибка конфигурации, а не успешный тест.

### 4.2. Начальные источники, которые уже установлены аудитом

- Активный business allowlist Big_landing_test: `https://rtk-internet.online/business`, `https://rtk-home.ru/business`, `https://online-beeline.ru/business`.
- Его connection allowlist также содержит бизнес-страницы: `https://moskva.beeline-ru.online/business`, `https://online-beeline.ru/business`, `https://beeline-internet.online/business`.
- В Everyday_test бизнес-флаги и города находятся в provider-конфигах; нужно перенести применимые бизнес-пути на Самару. Значения `Москва` и московские URL из старых конфигов не переносятся как целевой город нового теста.
- MTS business URL в Big_landing_test частично закомментированы. Они попадают в инвентаризацию со статусом blocked/excluded по подтверждённой причине; автоматически включать их нельзя.
- Формы с бизнес-чекбоксами могут находиться на обычных URL. Их необходимо инвентаризировать отдельно — business allowlist не является полным списком.

Это **начальные кандидаты из кода**, а не готовый подтверждённый список active. Проверенная разметка, контракты и данные для нового теста ещё не получены.

Дубликат объединяется только после подтверждения одинаковых самарских URL назначения, формы, бизнес-пути, режима выбора региона, окружения и контракта. Одинаковый провайдер или CSS-класс не доказывает эквивалентность. Исходные URL других городов сохраняются в source_refs, но не выполняются как live-кейсы; их неподтверждённый самарский аналог отмечается blocked. Различные формы/входы на одном домене не теряются при таком переносе.

### 4.3. Обязательный регион: Самара

Новое поле по задаче — пользовательский селект региона. Предоставленный фрагмент — отображающий `span`, а не HTML `<select>`; использовать `select_option()` для него нельзя.

```html
<span id="autocomplete_city_name" class="autocomplete-city-name" data-item="36401">Самара</span>
<input id="city-input" class="popup-select-city__input" type="text" placeholder=" " autocomplete="off">
<a class="region_item region_link" href="https://rtk-internet.online/samara" id="36401">Самара</a>
```

Это контракт из сообщения пользователя, не результат проверки живой DOM. Для указанной разметки проверять нормализованный текст `Самара` и `data-item="36401"` у `span#autocomplete_city_name.autocomplete-city-name` в целевой форме. При повторяющихся ID на странице локаторы ограничивать активной формой/попапом; не брать первый глобальный элемент.

**Маршрут R1 — бизнес-страница без региона на лендинге без регионального поддомена.**

1. Открыть бизнес-страницу из исходного скоупа и нужную форму.
2. Нажать реальную кнопку селекта региона, связанную с отображением `#autocomplete_city_name`; точный locator клика зафиксировать по DOM. Предоставленный span сам по себе не доказывает, что он является кнопкой.
3. В открытом попапе найти `input#city-input.popup-select-city__input` и ввести `Самара`. Не ориентироваться на пустой placeholder.
4. Дождаться единственной видимой ссылки `a.region_item.region_link[id="36401"]` с точным текстом `Самара`. Проверить href по контракту текущего домена; ссылка `https://rtk-internet.online/samara` дана для rtk-internet.online, не для всех сайтов.
5. Кликнуть эту ссылку и дождаться результата: обновления состояния или перехода, согласно адаптеру. Не выбирать первый результат по частичному совпадению названия.
6. Учесть, что `/samara` в примере — городской URL, а не доказательство открытия бизнес-страницы. Если выбор увёл из бизнес-контекста, открыть подтверждённый самарский business URL/вернуть целевую форму штатным маршрутом, сохранив выбор. Нельзя автоматически приписывать `/business` к неизвестному URL.
7. Повторно найти целевую форму после перехода/перерисовки; проверить Самару по тексту и ID. Проверить ещё раз после заполнения и непосредственно перед submit.

Выбор через попап — обязательная часть R1, даже если исходно показана Самара; такая проверка не должна ускоряться предустановкой cookie или прямым изменением data-item.

**Маршрут R2 — сайт с региональными поддоменами.**

1. Сразу открыть проверенный URL бизнес-страницы Самары из реестра. Не заходить сначала в Москву и не переключать регион через список городов.
2. Подтвердить конечный host/path по самарскому маршруту и регион целевой формы: текст `Самара`, UI ID `36401` для указанного нового поля.
3. После переключения бизнес-режима и заполнения повторить контроль региона перед submit.

Наличие точки в hostname не определяет R2: схема региональных поддоменов — свойство конкретного лендинга. Адреса вида `samara.<домен>/business` нельзя объявлять существующими без проверки источника/навигации сайта.

**Общий запрет:** R1/R2 распространяются также на формы с чекбоксом «Для бизнеса / в офис» на обычных страницах. Никакого fallback на Москву, текущий город по IP или первый доступный город. Не найден или не подтверждён регион Самара — остановить кейс до отправки.

**Контроль отправляемого региона:** непосредственно перед кликом подтвердить UI; перед фактической передачей целевого запроса проверить регион в его контракте. Неизвестный или другой регион — отменить запрос и FAIL, а не сначала отправить в другой город и затем отчитаться об ошибке. UI ID `36401` не объявляется автоматически именем/значением backend-поля: соответствие сетевому контракту требует проверки. Подмена значения региона в перехваченном запросе запрещена — это скрыла бы дефект формы.

## 5. Сценарии выполнения

### BIZ-01. Бизнес-заявка с бизнес-страницы

1. Создать изолированный browser context для кейса.
2. Выполнить вход по region_mode: исходная бизнес-страница для R1 либо прямой самарский URL для R2; проверить конечный URL.
3. Закрыть только известные мешающие оверлеи.
4. Открыть целевую форму по заданному триггеру либо найти inline-форму.
5. Проверить соответствие формы записи реестра и выполнить выбор/контроль Самары по R1/R2. После регионального перехода повторно получить локаторы формы.
6. Если у формы есть бизнес-переключатель, выполнить его сценарий по BIZ-02.
7. Заполнить необходимые поля и только явно описанные согласия.
8. Проверить Самару и бизнес-состояние перед кликом; зарегистрировать проверку региона до передачи запроса, наблюдение за целевым запросом и ответом.
9. Отправить форму один раз, разрешив передачу только запроса с подтверждённым регионом Самара.
10. Проверить фактическое бизнес-назначение и регион запроса, связанный положительный ответ и ожидаемое UI-подтверждение.
11. Сохранить результат; завершить context без возврата на главную.

Сам URL /business не считается достаточным доказательством бизнес-назначения.

### BIZ-02. Заявка через «Для бизнеса / в офис»

1. Выполнить подготовку формы, как в BIZ-01.
2. Найти конкретный бизнес-control; отсутствие или недоступность ожидаемого элемента — ошибка.
3. Зафиксировать исходное состояние. Если ожидаемый default подтверждён контрактом, проверить его; иначе не придумывать default.
4. Проверить переключение туда и обратно **без отправки обычной заявки**:
   - checkbox: выключен → включён → выключен → включён;
   - radio: подтверждённый небизнес-вариант → бизнес → небизнес → бизнес.
   - Для иного устройства управления последовательность задаёт адаптер по реальной разметке.
5. На каждом переходе проверить checked/selected и известные зависимые поля. Недоступное допустимое обратное состояние нельзя выдумывать — адаптер должен описать реальные возможности элемента.
6. Заполнить поля в окончательном бизнес-состоянии; вновь проверить бизнес-состояние и регион Самара перед submit. Переключение услуги не должно сбрасывать город.
7. Выполнить ровно одну бизнес-отправку и проверки BIZ-01.

«Для бизнеса» и «В офис» — пользовательские подписи. Соответствие label, name, value и признаку запроса подтверждается для каждого адаптера, а не задаётся глобальным предположением.

## 6. Правило успешности

**PASS кейса = правильная форма + Самара в форме + бизнес-состояние + целевой запрос с бизнес-признаком и регионом Самара + связанный положительный ответ + ожидаемое UI-подтверждение.**

- Обычная заявка и бизнес-заявка оцениваются раздельно; успех соседнего кейса ничего не меняет.
- Проверяется фактический outgoing payload. Значение из параметров теста не является доказательством того, что оно отправлено.
- Бизнес-признаком может быть поле/набор полей или отдельный endpoint — только по подтверждённому контракту.
- Ответ связывается с конкретным запросом и текущей формой; старый success URL, ответ другого попапа или произвольный CF7 mail_sent не подходят.
- Переход на Thanks без подтверждения целевой отправки не даёт PASS.
- Бизнес-признак есть, но сервер отклонил запрос — FAIL.
- Исчезновение формы или бизнес-control — FAIL, а не «неприменимо».
- Ожидаемый активный кейс не выполнен из-за бюджета или инфраструктуры — незелёный итог.
- Пустая выборка по фильтру — ошибка запуска.
- Для выбранной области должны быть видны active, blocked и excluded. Наличие blocked означает неполное покрытие; excluded допустим только как явное согласованное исключение.
- Прохождение всех active не означает полного покрытия при наличии blocked.

Быстрый тест подтверждает отправку бизнес-заявки и принятие целевым обработчиком. Проверка последующей доставки в CRM/состояния хранения — отдельный уровень. Если контракт конкретной формы требует такой проверки, включить узкий запрос по ID в её сценарий и учесть его время; не заявлять этот уровень проверенным без фактической проверки.

## 7. Скорость и независимость

Предлагаемый первый профиль: Chromium desktop, полный список active бизнес-кейсов выбранной области, один worker. Другие браузеры, мобильный профиль и параллельность — отдельные параметры, а не обязательное перемножение каждого запуска.

Ускорение достигается за счёт:

- прямых самарских бизнес-URL для R2; для R1 — одного обязательного выбора Самары через попап вместо перебора городов;
- целевой формы вместо цикла по всем кнопкам;
- одной отправки вместо полного перебора услуг;
- объединения только доказанных дубликатов между двумя репозиториями;
- ожиданий состояния и ответа вместо фиксированных sleep;
- одного browser process на worker и отдельного context на кейс;
- отсутствия повторных отправок при неоднозначном результате.

**Предлагаемый бюджет:** общий жёсткий лимит 75 секунд на кейс, включая подготовку и ожидания; ориентир p95 ≤ 60 секунд на исправном согласованном окружении. Эти числа требуют замера, это не обещание текущей скорости.

Предлагаемые бюджеты фаз с учётом Самары: входная навигация ≤ 15 с, открытие формы ≤ 10 с, выбор/проверка региона с возможным переходом ≤ 15 с, переключение/заполнение ≤ 15 с, отправка/подтверждение ≤ 15 с; действует также общий deadline 75 с. Все повторы открытия входят в этот deadline. Это верхние границы, а не обязательные задержки; отдельно замерять R1 и R2, не пропускать выбор города ради бюджета.

Время всего запуска измеряется как функция числа кейсов N и worker-ов W. Плановая верхняя оценка: `ceil(N / W) × 75 с + измеренный overhead`. Overhead включает старт/завершение браузера и подготовку отчёта; создание окружения и установку зависимостей измерять отдельно. Число кейсов нельзя сокращать только ради красивого времени.

Повторный submit автоматически не выполняется: при отправленном запросе и потерянном ответе результат фиксируется как неподтверждённый. Повторить подготовку до первого submit можно только в общем бюджете и без отправки посторонней формы.

## 8. Данные и окружения

- Запуск явно задаёт stage или prod; не переносить данные и URL между ними по предположению.
- Тестовые телефоны, адреса, обязательные реквизиты и правила обработки тестовых заявок берутся из согласованного профиля. Адресные данные должны относиться к Самаре, включая ID улицы/дома при их использовании. Московские данные старого sender не признаются автоматически подходящими.
- Данные для данного окружения должны быть проверены до live-прогона; при отсутствии — ошибка подготовки, без submit.
- Секреты хранятся в CI credentials. В диагностике маскировать телефон и персональные поля, сохранять бизнес-признак и техническую корреляцию.
- Расписание и внешние уведомления не создаются в рамках этой спецификации; новый CI job проектируется независимым.

## 9. Приёмка

| ID | Критерий |
|---|---|
| AC-01 | Новый репозиторий запускается из чистого checkout без файлов, импортов и job-ов Everyday_test/Big_landing_test |
| AC-02 | Для каждого исходного бизнес-пути есть запись «перенесён / объединён с доказательством / blocked / excluded с решением» |
| AC-03 | Каждый active кейс — отдельный pytest item с собственным результатом |
| AC-04 | Каждый успешный кейс выполняет одну целевую бизнес-отправку в Самаре; подготовка не создаёт сторонних заявок |
| AC-05 | Для бизнес-control проверяются фактическое состояние и бизнес-признак outgoing запроса |
| AC-06 | Неверный бизнес-признак, отсутствующий control и ошибка ответа приводят к незелёному итогу даже при успехе соседнего кейса |
| AC-07 | Пустой набор, blocked в выбранной области и незавершённые active не выдаются за полное успешное покрытие |
| AC-08 | Основные тесты после миграции не отправляют бизнес-заявки через /business, Place, чекбоксы или формы с иным техническим именем |
| AC-09 | Основные небизнес-проверки сохраняются; не удаляются целиком connection/checkaddress только из-за бизнес-ветки |
| AC-10 | Представлены измерения N, W, длительностей кейсов, общего времени и сравнение с исходным бизнес-путём при одинаковом покрытии |
| AC-11 | Реальные значения контрактов и тестовых данных задокументированы; placeholders не попадают в active |
| AC-12 | Кейс, прошедший лишь UI-подготовку, не обозначается как успешно отправивший заявку |
| AC-13 | Все active кейсы фиксируют target_city=Самара; CLI/CI не допускает отправку в другой город |
| AC-14 | R1 выбирает Самару через кнопку региона, city-input и точную ссылку id=36401; после возможного перехода подтверждается целевая бизнес-форма |
| AC-15 | R2 сразу открывает проверенную бизнес-страницу Самары на региональном поддомене и проверяет город в форме |
| AC-16 | Перед submit текст региона Самара и data-item=36401 подтверждены в целевой форме; после перерисовки проверка повторяется |
| AC-17 | Другой/неизвестный регион outgoing запроса блокируется до передачи серверу; в тесте такой ошибки число переданных заявок равно нулю |
| AC-18 | Список бизнес-путей получен из скоупов обоих старых тестов; исходные города преобразованы в проверенные самарские цели или явно отмечены blocked |

## 10. Что предстоит установить при реализации

| Неизвестно | Влияние |
|---|---|
| Соответствие бизнес-путей из исходных скоупов конкретным самарским URL и формам | Определяет active реестр и N; источник списка уже задан пользователем |

| Разметка «В офис», связь с Place/checkbox | Определяет адаптер; label нельзя подменять value |
| Проверенные stage URL и профили тестовых данных | Блокирует соответствующий live-запуск |
| Основания текущих MTS исключений | Не даёт автоматически включить или забыть эти кейсы |
| Потребность в подтверждении записи в CRM, а не только принятии формы | Определяет глубину конкретного кейса и бюджет |
